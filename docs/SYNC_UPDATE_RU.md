# Единый пакет серверной синхронизации

Подготовлен поверх ветки `feature/offline-sync`, коммит `1e76fa2`.
Изменения в GitHub не отправлялись. Старые миграции V1–V9 не изменены.

## Что входит

- Удаление категории через команду синхронизации, проверка версии и безопасный повтор.
- Запрет личной офлайн-очереди изменять счета, открытые группе, и операции на них.
  Обычные API для работы с группами онлайн остаются доступными.
- Полная личная выгрузка и последующие изменения с удалениями.
- Согласованный снимок данных, неизменяемые страницы по 200 элементов.
- Курсор, учитывающий транзакции, завершившиеся после предыдущей выгрузки.
- Журнал PostgreSQL: изменения через веб и обычный API тоже учитываются.
- Ограничение срока хранения выгрузок, безопасная очистка журнала.
- Интеграционные тесты и описание клиентского протокола в `docs/OFFLINE_SYNC.md`.

Это пакет по личной синхронизации. В него не входят мобильный клиент, стандартные
коды категорий, подписки, Apple Login и отдельная неизменяемая история группы.

## Как применить

В архиве есть два альтернативных способа:

- `sync-completion.patch` — единый патч для Git.
- `files/` — готовые полные версии всех новых и изменённых файлов, с исходными путями.

Применять нужно **один** из этих способов.

### Вариант 1: патч

Сохрани `sync-completion.patch` в Downloads. В терминале перейди в свой репозиторий.
Убедись, что последние локальные изменения сохранены и закоммичены. Затем:

```sh
git switch feature/offline-sync
git pull --ff-only origin feature/offline-sync
git status --short
```

Если последняя команда ничего не выводит, рабочая копия чистая. Проверь патч:

```sh
git apply --check "$HOME/Downloads/sync-completion.patch"
```

Если ошибок нет, примени:

```sh
git apply "$HOME/Downloads/sync-completion.patch"
```

`git apply` меняет файлы, но не создаёт коммит и не делает push.
Если проверка не прошла, не применяй `--reject` и не затирай файлы: скорее всего,
рабочая версия отличается от исходного коммита. Сначала нужно сопоставить различия.

### Вариант 2: полные файлы

В распакованном архиве содержимое папки `files/` нужно перенести в корень репозитория,
сохранив пути. Существующие файлы заменить, новые добавить. Для каждого файла
нужна только одна замена. Не удаляй остальные файлы проекта.

Не копируй папку `files` целиком как подпапку проекта: внутри неё находятся `src/`
и `docs/`, которые должны попасть на соответствующие места в репозитории.

## Одна команда проверки

Запусти Docker Desktop и выполни:

```sh
./mvnw clean verify
```

Это запускает весь существующий набор и новые тесты. Отдельно менять старые тесты
или устанавливать Maven не нужно. Зависимости и pom.xml пакет не меняет.

### Что проверено при подготовке

- Синтаксис Java-файлов, SQL и PL/pgSQL: проверен.
- Последовательное применение V1–V10: прошло на PostgreSQL-движке PGlite 18.6.
- Девять групп проверок реального SQL: прошли. Полная/последующая выгрузка,

  открытие/отзыв доступа группы, связанные чужие категории, подписи переводов,

## Проверка локального dev

После успешных тестов:

```sh
docker compose up -d postgres
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
```

Приложение само применит новую миграцию V10. Проверить её в другом терминале:

```sh
docker compose exec postgres psql -U family_budget -d family_budget \
  -c "SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;"
```

Должна появиться успешная версия `10 — create sync downloads`.
Новые объекты: `sync_change`, `sync_download`, `sync_download_item`, представление
`sync_personal_entity` и функции/триггеры журнала.

Старые данные не удаляются. Полная первоначальная выгрузка читает их из существующих
таблиц; журнал нужен для последующих изменений.

## Что важно для мобильного клиента

Подробный контракт — в `docs/OFFLINE_SYNC.md`.

1. Отправить очередь команд с постоянными UUID команд. Зависимые создания — после
   создания соответствующих счетов/категорий.
2. Создать выгрузку через `POST /api/sync/downloads`: первый раз `{"cursor":null}`.
3. Получить все страницы через `GET /api/sync/downloads/{id}?after=0`, далее использовать
   возвращённый `nextAfter`.
4. Применить данные и последний `nextCursor` одной локальной транзакцией.
5. Подтвердить завершение: `POST /api/sync/downloads/{id}/complete`.
6. Следующую выгрузку начать с сохранённым курсором.

Страницы доступны до 24 часов, курсор — 7 дней. Более долгий офлайн не запрещён:
понадобится полная выгрузка. При этом нельзя стирать локальную очередь и неотправленные
изменения. «Полная выгрузка» означает замену серверного зеркала с последующим согласованием
локальных изменений, а не удаление пользовательских данных на телефоне.

Завершай выгрузку после применения: её JSON-страницы временно занимают место в БД.
Успешные команды и отметки удаления автоматически не очищаются, чтобы старый телефон
не мог повторно списать деньги или восстановить удалённую сущность.

Предыдущие нагрузочные результаты относятся к прежним API: новые выгрузки и накладные
расходы триггеров ещё нужно измерить отдельно. Пакет нельзя считать проверенным на нагрузку
только на основании старого прогона k6.

После проверки можно сделать обычный коммит в рабочей ветке. Автоматический деплой,
завязанный на main, от применения локального патча или push в feature не запускается.
